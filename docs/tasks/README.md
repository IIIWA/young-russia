## Запуск и контроль

1. Пользователь запускает работу; управляющий выбирает чат из roster и передаёт короткое поручение по форме ниже. Рабочие уточнения внутри порученного результата покрывает действующее разрешение на оркестрацию.
2. Исполнитель читает текущий реестр и brief, затем только относящиеся к задаче ссылки. В сообщении передаются новые данные и изменившиеся ограничения; полная история не копируется. Рабочая папка — `C:/Users/Иван да Марья/Desktop/VibeCoding/young-russia`; ссылки разрешаются относительно неё.
3. Управляющий фиксирует в TASKS настоящий ID, запуск, разрешённые файлы и зависимости. По общему правилу `~/.codex/AGENTS.md` независимые разрешённые части выполняются параллельно: управляющий использует существующие чаты по ролям, исполнители обязательно одновременно вызывают субагентов и проверяют их выводы. Один writer на общий набор файлов и Git; обоснованная последовательность фиксируется в brief/TASKS назначенным writer. Текущая папка сохраняется; worktree — по явному запросу пользователя.
4. Исполнитель возвращает краткий результат с доказательствами и QA. Управляющий читает их, принимает либо задаёт исправление внутри разрешённого объёма; назначенный writer обновляет единый реестр и пересекающиеся стратегические статусы.
5. После результата исполнитель останавливается. Следующий этап, новая задача или автоматизация требуют отдельного запуска.

Форма поручения в постоянный чат:

```text
Цель: результат текущего разрешённого этапа.
Новые данные: изменения с прошлого отчёта; ссылки на brief/evidence.
Запись: один writer, разрешённые пути и существенные границы.
Готовность: проверяемый критерий и ссылка на требуемую QA.
Зависимость: что требуется до действия; где можно идти параллельно.
```

Поручение может назвать ID или описать нужный результат: управляющий присваивает ID и ограничивает область исполнителей. Git, публикация и новые доступы определяются объёмом поручения; для SSH действует постоянная политика в AGENTS.md.

## Контекст и стоимость

Короткий dispatch и ссылки выбраны как рабочая дисциплина проекта. OpenAI описывает накопление контекста в длинных чатах и compaction для сохранения полезного состояния ([Codex context lifecycle](https://developers.openai.com/blog/mastering-codex-remote-for-engineering#7-manage-context-before-it-becomes-a-problem)); API compaction переносит ключевое состояние меньшим числом токенов ([документация](https://developers.openai.com/api/docs/guides/compaction)). Это не обещание бесплатной старой истории или гарантированной экономии при reuse. Здесь compaction, новые настройки и автоматизации не запускаются; нужны только актуальные brief и evidence по ссылкам.

## Формат результата исполнителя

- Результат и его граница, фактические изменённые пути.
- Ссылки на evidence/QA по критериям; неизвестное или внешняя зависимость.
- Отдельные состояния local/Git/GitHub/production и следующий шаг, который ещё не запущен; исходная ревизия берётся из уже разрешённых доказательств, новый Git-доступ ради отчёта не требуется.

Не включать токены, пароли, ключи, приватные контакты и необработанные внутренние заметки в публичный отчёт. `AGENTS.md` отслеживается Git; большинство внутренних Obsidian/evidence-файлов остаётся локальным по ignore-правилам. Передавать только явно проверенную allowlist текущего задания: присутствие локального файла само по себе не включает его в новый checkout.
