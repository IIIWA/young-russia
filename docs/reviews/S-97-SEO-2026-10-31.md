### 2. Сейчас: WebSite + WebPage, сохранив BreadcrumbList

На главной добавить один WebSite с `@id=https://young-russia.ru/#website`, `url`, `name=ПМК Петербурга`, `inLanguage=ru`. Имя уже используется в header и og:site_name. Не придумывать альтернативный бренд или официальный статус. Google использует WebSite на корневой главной как сигнал предпочтительного имени; это не гарантия выбора имени, тем более общее описательное имя может не быть выбрано. [Google: site names](https://developers.google.com/search/docs/appearance/site-names).

Для существующих страниц безопасен WebPage: стабильный `@id=<canonical>#webpage`, `url=canonical`, `name=title`, `description`, `inLanguage=ru`, `isPartOf` со ссылкой на WebSite. BreadcrumbList сохранить, дать ему `@id=<canonical>#breadcrumb`, связать через `WebPage.breadcrumb`. На главной breadcrumb не изобретать. Это семантическая рекомендация по [WebSite](https://schema.org/WebSite) и [WebPage](https://schema.org/WebPage); сама по себе не обещает rich result или попадание в ответы ИИ.

Не добавлять Organization/LocalBusiness, муниципальное авторство, publisher, автора, рейтинги, часы работы, фиктивный SearchAction или дату проверки, выведенную из даты сборки. Перечень отражает только уже наблюдаемые свойства сайта и страниц. Связь через @id и несколько типов допустимы; разметка должна соответствовать содержимому. [Google: structured data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies).

Текущий `check-seo.mjs` считает каждый JSON-LD скрипт отдельным BreadcrumbList. При переходе на @graph управляющему нужно проверять узлы и связи вместо сохранения этого старого предположения: один WebPage/self URL, один breadcrumb для неглавной, последовательность позиций, правильная последняя ссылка, уникальные ID, корневой WebSite и отсутствие выдуманных типов/свойств.
